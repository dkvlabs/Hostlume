# ADR-0009 — Multi-host protocol v1: pairing, TLS pinning and per-device tokens

**Status:** accepted (phase 10, optional post-v1)
**Date:** 2026-10-19
**Context:** FX-022, `docs/phases/10-multi-host-extension.md`, ADR-0008 (LAN gate), `docs/security-privacy.md` §6

## Threat model (phase 10 §1 — written before code)

**Assets.** Agent telemetry (the numeric projection from ADR-0008 plus a user-chosen display name), the
per-device bearer tokens a console uses against an agent, the agent's owner token, the agent's TLS
private key, the console's host list + device tokens, and local history rows stored under a remote
`host_id`.

**Adversaries and mitigations.**

| # | Adversary / failure | Mitigation (and the test that pins it) |
|---|---|---|
| A1 | Passive LAN observer | LAN mode is HTTPS only (rustls 0.23, ring provider, TLS 1.2/1.3). Plain HTTP exists only on loopback, as before. |
| A2 | Active MITM **during pairing** presents its own certificate | The pairing proof is an HMAC keyed by the pairing code over the TLS certificate fingerprint the console actually observed. The agent verifies the proof against **its own** fingerprint, so a proof computed over an attacker certificate never validates — and the attempt burns the code. `pairing::tests::proof_bound_to_another_fingerprint_is_rejected_and_burns`, integration `mitm_at_pairing_fails_and_burns_code`. |
| A3 | Active MITM **after pairing** | The console pins the SHA-256 of the agent's DER certificate; any other certificate fails the handshake before an HTTP request — and therefore the bearer token — is ever sent. Integration `compromised_lan_device_never_receives_the_token`. |
| A4 | Online pairing-code guessing | Code = 8 symbols from a 32-symbol alphabet (40 bits) from the OS RNG; single-use; 120 s TTL; **one attempt per code** (any failure burns it); per-IP auth rate limit 10/10 s. Offline guessing has nothing to attack: the only observable (a proof) is already burned. `pairing::tests::*`, integration `wrong_code_burns_the_window`. |
| A5 | Token theft from the console's disk | Device tokens live in a dedicated restricted file (`remote-credentials.json`, mode 0600 on unix), never in the settings SQLite, never sent to the WebView, redacted from diagnostics. Per-device revocation on the agent invalidates a stolen token immediately. Follow-up: OS keychain storage. |
| A6 | Token theft from the agent's disk | The agent stores only SHA-256 hashes (same as the owner token). |
| A7 | Replay | TLS prevents capture; the proof carries a console nonce and the code is single-use. |
| A8 | Rogue agent impersonating a host | The agent must return an acknowledgement HMAC (same key, distinct domain string) proving it also knows the code; the console aborts otherwise and never stores a token. `pairing::tests::ack_proof_round_trip`. |
| A9 | Duplicate host identity | The console refuses to pair a `host_id` that is already paired at a different endpoint (the user removes the old entry first); re-pairing the same `host_id` at the same endpoint replaces the token. Integration `duplicate_host_id_is_refused`. |
| A10 | Clock skew, stale data presented as live | Staleness comes from the console's own receipt clock; remote timestamps are displayed as reported, with the computed skew, and never drive the live/stale decision. `client::tests::status_is_derived_from_local_receipt_time`, UI test "stale is never rendered as live". |
| A11 | Discovery exposure | **No** mDNS/broadcast in v1 — endpoints are typed in. Agent LAN mode is off by default. Unauthenticated surface in LAN mode = `POST /api/v1/pair` (rate-limited, code-gated) and the static dashboard HTML (no data). |
| A12 | Resource exhaustion | ≤ 8 paired hosts, bounded ring buffers per host, 5 s request timeouts, exponential backoff 2–60 s, a single pairing window at a time. |

Out of scope by design: public-Internet relay, cloud broker, port forwarding, and any fleet control —
there is no route that executes, terminates, deletes or adjusts anything on a remote host.

## Decision

1. **Protocol version.** `monitor_remote::protocol::PROTOCOL_VERSION = 1`. `GET /api/v1/manifest`
   (authenticated) returns `{protocol_version, agent_version, host_id, display_name, cadence_ms,
   families, tls_fingerprint_sha256}`. The console refuses a different major version with the typed
   `incompatible` state. `display_name` is user-chosen; the OS hostname, serials and MACs never appear.
2. **Transport.** LAN mode serves HTTPS with a self-signed ECDSA P-256 certificate generated by `rcgen`
   at first LAN enable and persisted as DER (`remote-tls/cert.der`, `remote-tls/key.der` 0600). Loopback
   mode is unchanged (HTTP). The console's rustls verifier pins the certificate fingerprint and verifies
   handshake signatures through the ring provider; hostname and validity period are not part of the
   trust decision (pinning is). ADR-0008's "LAN fails closed" gate is lifted **only** for this TLS path.
3. **Pairing.** The agent user opens a pairing window (code shown in the agent UI). The console sends
   `POST /api/v1/pair {protocol_version, device_id, device_label, nonce, proof}` with
   `proof = HMAC-SHA256(code, "hostlume-pair-v1" ‖ device_id ‖ nonce ‖ fingerprint_hex)`. On success the
   agent returns `{device_token (once), host_id, display_name, protocol_version, ack}` with
   `ack = HMAC-SHA256(code, "hostlume-pair-ack-v1" ‖ device_id ‖ nonce ‖ fingerprint_hex)`.
   Constant-time comparison; one attempt per code.
4. **Device tokens.** Per-device UUID v4 bearer tokens; the agent persists `{device_id, label,
   token_hash, created_at}` and tracks last-seen in memory; revocation removes the hash and takes effect
   immediately (hot-swapped in `ServerShared`). The owner token keeps its phase-08 semantics.
5. **Ingestion.** The console polls `/api/v1/snapshot` per host on a dedicated thread; host state
   `never_connected → online → stale → offline`, plus the terminal `unauthorized`, `cert_mismatch` and
   `incompatible` states that require user action. Optional per-host history recording writes into the
   shared history database under the remote `host_id`; removing a host can delete those rows.
6. **Not in v1.** Discovery, keychain storage, SSE-based ingestion, remote Applications/Storage pages,
   Windows/Linux runtime validation.

## Consequences

* New dependencies in `monitor-remote`: `rustls` 0.23 (ring, std, tls12), `tokio-rustls` 0.26 (ring),
  `rcgen` 0.13 (ring), and `ureq` 2.12 promoted from dev to runtime (tls, json). `aws-lc-rs` is not
  enabled anywhere in the workspace.
* HMAC-SHA256 is implemented over the existing `sha2` crate (RFC 2104) and pinned by an RFC 4231 test
  vector rather than adding another crypto crate.
* Settings schema moves to v9 (`remote.display_name`, `remote_devices`, `remote_hosts`); the settings
  contract fixture is regenerated.
