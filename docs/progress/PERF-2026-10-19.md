# Performance measurement — 2026-10-19 (phase 09 §2.6)

**Build:** release bundle `APP_NAME.app` 0.1.0, arm64, built from the phase 09 working tree (parent commit `9e9f252`; the phase 09 commit records the exact SHA).  
**Hardware / OS:** Apple M3 Max (14 logical cores), 36 GiB, macOS 27.0.1 (26A434). Laptop on AC.  
**Method:** `ps -o rss` for the main process every 30 s; `top -l 2 -s 1 -stats cpu` for the main process's instantaneous CPU; the WebKit content process attributed by start time (spawned within 60 s of the app) and sampled with `ps -o rss`; `history.sqlite3` size via `stat`. Sampler script kept outside the repository (`/tmp/hostlume-soak/sampler.zsh`); raw CSVs retained in that directory for this session. Concurrent activity on the machine: the owner was using it interactively, and this session ran `cargo`/`vitest`/`vite` jobs intermittently — the numbers are therefore an upper bound on quiet-machine behaviour, not a clean-room benchmark.

Two runs were taken because the first exposed two frontend defects (see docs/progress/PHASE-09.md §3) that left the dashboard frozen; the second run is the fixed release candidate.

## Results

| Run | Duration | State of UI | Main RSS min / avg / max | WebKit content RSS min / avg / max | Main CPU avg / max | History DB growth |
|---|---|---|---|---|---|---|
| 1 — release build before fixes | 30 min (60 samples) | Overview window open but **frozen on the first tick** (defects below) | 49.9 / 61.3 / 83.0 MB | 21.5 / 41.3 / 93.1 MB | 0.50 % / 3.0 % | +39.2 MB (1.24 MB/min) |
| 2 — release candidate (fixed) | 10 min (20 samples) | Overview window open, **live** (refresh every 3 s, sparklines) | 85.2 / 99.4 / 117.0 MB | 63.8 / 86.2 / 107.0 MB | 0.43 % / 3.9 % | +12.5 MB (1.23 MB/min) |

- **CPU:** main-process average 0.4–0.5 %, peaks ≤4 % (WebKit content-process CPU was not measured). Inside the proposed `<2 %` target (testing-qa.md §5).
- **Memory:** the main process alone is within the proposed `<150 MB`; counting the WebKit content process that renders the live dashboard, the total is **≈185 MB average** with the window open — **above** the proposed target. The target was declared "measured, not guaranteed"; results and the plan below are documented as §4 of the phase requires.
- **Startup:** first real snapshot applied **3 s** after launch (first tick); first medium-group readings (memory/disks) at 10 s.
- **Lifecycle:** run 2 exited with **code 0** on an OS quit after 12.5 min; no `crash.log` was written in either run (no panics); both SQLite databases pass `PRAGMA integrity_check`; the remote port was never opened (default OFF). Run 1 ended between 17:42Z and 17:58Z without a panic or macOS crash report; it had been launched via `open`, so no exit status was captured, and the owner was actively using the machine at the time — the cause was not determined (see PHASE-09 §5).

## History database growth — needs a decision before general release

Measured write rate: **4,860 raw rows/min across 180 active numeric series** (every reading of every snapshot is persisted; the slow/medium groups re-publish on every fast tick), ≈**250 bytes per row including the two indexes** (host_id and generation are 36-byte UUID strings and `source` is repeated per row). That is **≈73 MB/hour**.

With the default raw retention of **24 h** the raw table plateaus at roughly **1.7–1.8 GB** per host (SQLite reuses freed pages; the file does not shrink without `VACUUM`). Growth is **bounded** by retention, so this is not an unbounded-growth release blocker, but it is far larger than a monitoring tool should need and was never measured before this phase.

Plan (not applied in phase 09 — retention defaults are a product decision):

1. Lower the default raw horizon (e.g. 24 h → 6 h ≈ 440 MB) and/or persist slow-group readings only when they change.
2. Normalise `host_id`, `generation` and `source` into integer-keyed lookup tables (`metric_definitions` already exists for this purpose) — estimated −40 % bytes/row.
3. Enable `PRAGMA auto_vacuum = INCREMENTAL` on new databases so the file follows retention.

## Not measured in this phase

- 4-hour soak (only 30 + 10 min runs).
- Window hidden / close-to-tray mode, compact monitor, open Compare charts, recording active, remote stream with multiple clients.
- WebKit content-process CPU.
- Large folder scan throughput and the 1 M-point history fixture.
- Any non-macOS target (no hardware).
